## 1. Exact inventory

Security Advisor returned **90** `auth_allow_anonymous_sign_ins` findings. The findings map to **90 distinct tables/relations** and **364 policies**. This is a policy/role warning inventory, not 90 proven data leaks.

| Measure | Current result |

| Relations with at least one authenticated policy | 89 |
| Relations with a restrictive policy whose predicate explicitly checks `is_anonymous` | 46 |
| Relations with permissive policies but no detected table-wide restrictive `is_anonymous` guard | 40 |
| Relations with at least one policy targeting `anon` or `public` | 8 |
| Relations with effective direct anon SELECT | 5 |
| Relations with effective direct anon INSERT grant | 1 |
| Relations with a restrictive literal-false policy | 5 |
| Relations with multiple permissive policies (OR composition needs review) | 51 |
| Relations with no RLS policy in this Advisor set | 0 |

**Important semantics:** Supabase anonymous Auth users use the PostgreSQL `authenticated` role with JWT claim `is_anonymous=true`. Therefore `auth.uid()` alone is not proof that a session is a confirmed user. Conversely, an Advisor warning alone is not proof of access: row predicates, table/column grants, and restrictive-policy AND composition must all be considered.

## 3. Sensitive unguarded-policy review queue

These 40 relations have at least one permissive policy but no detected table-wide restrictive predicate explicitly checking `is_anonymous`. This is a **test queue**, not a vulnerability count. Many predicates bind to `auth.uid()` and active tenant membership; those must be tested using an anonymous Auth JWT because `auth.uid()` is non-null for anonymous users.

High-priority families:
- **Payments/finance/wallet/settlement:** `commission_rules`, `commission_transactions`, `general_ledger`, `journal_entries`, `journal_entry_lines`, `mantigo_financial_config`, `mantigo_financial_ledger`, `mantigo_rate_limit_config`, `payment_events`, `payment_financial_reconciliations`, `payment_intents`, `payment_provider_events`, `refund_transactions`, `settlement_attempts`, `settlement_transactions`, `wallet_accounts`, `wallet_transactions`.
- **Medical/support/customer communication:** `medical_appointments`, `notifications`, `support_tickets`, `ticket_messages`.
- **MantiGO and provider/customer flows:** `indrive_bids`, `indrive_requests`, `mantigo_captain_profiles`, `marketing_leads`, `marketing_projects`, `marketing_provider_profiles`, `push_subscriptions`.
- **Digital pages and SMM:** `digital_page_orders`, `digital_page_products`, `digital_page_sections`, `digital_pages`, `smm_order_events`, `smm_orders`, `smm_wallet_transactions`, `smm_wallets`, `subscription_payment_intents`.
- **Public/storage surfaces:** `objects` (Storage), `platform_brand_assets`, and `platform_geo_areas`.

Additional note: the `indrive_requests` and `indrive_bids` SELECT predicates explicitly reject anonymous JWTs, but UPDATE/DELETE policies still include the legacy `is_platform_admin()` branch. That is tracked separately under P0 #867/RC484 and must not be marked fixed by this matrix. The MantiGO financial config policies rely on `mnty_can_platform_admin()`, which remains a live Production deployment gap tracked under #867/RC464/RC471.
