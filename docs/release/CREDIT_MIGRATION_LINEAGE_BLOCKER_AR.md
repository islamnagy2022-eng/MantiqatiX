# مانع سلسلة ترحيلات الائتمان — تقرير الأدلة وخطة الحل

**التاريخ:** 2026-10-13  
**الحالة:** BLOCKED — لا يوجد خط أساس تاريخي معتمد  
**النطاق:** `credit_policies`, `credit_accounts`, `credit_periods` وسلسلة الترحيلات التي تعتمد عليها.

## 1. لماذا لا نُنشئ baseline تلقائيًا؟

أوقف فحص إعادة تشغيل الترحيلات في CI طلب الدمج #207 عند التحقق القبلي بسبب غياب خط أساس تاريخي معتمد للجداول الثلاثة. لم تكن هذه النتيجة فشلًا في تنفيذ الترحيل نفسه؛ إذ لم تصل العملية إلى مرحلة تطبيق سلسلة الترحيلات.

الأرشيف المرفق `source_RC40.zip` يحتوي:
- `20260920185000_production_credit_control.sql` — إنشاء الجداول الثلاثة.
- `20260920190000_harden_credit_status_authorization.sql` — دالة `get_credit_status` وسياسة تنفيذها.

لكن الأرشيف لا يثبت أنه المصدر التاريخي المطابق لما طُبق في الإنتاج. لذلك لا يجوز استخدامه كمرجع حاسم أو توليد baseline تاريخي منه دون إثبات provenance.

## 2. فروق موثقة بين DDL الأرشيف ولقطة الإنتاج السابقة

| الخاصية | DDL الأرشيف | لقطة الإنتاج السابقة | القرار |
|---|---|---|---|
| أنواع مبالغ الائتمان | `numeric(14,2)` | `numeric(18,2)` | اختلاف فعلي؛ لا توحّد النوع تلقائيًا |
| `grace_days` | default 7 | default 0 | اختلاف فعلي |
| `suspend_after_days` | default 30 | default 15 | اختلاف فعلي |
| `block_new_credit` | default false | default true | اختلاف ذو أثر تجاري/أمني |
| قيد تواريخ الفترة | لم يظهر قيد `period_end >= period_start` في DDL الأرشيف | قيد موجود في الإنتاج | اختلاف فعلي |
| RLS / FORCE RLS | مفعّل على الجداول الثلاثة | مفعّل على الجداول الثلاثة | تطابق جزئي فقط |

هذه مقارنة بين مصدر أرشيفي ولقطة إنتاج سابقة، وليست شهادة بأن أيًا منهما هو التاريخ الأصلي الكامل. يلزم إعادة قراءة حية قبل أي قرار تنفيذي.

## 3. ما الذي تم التحقق منه من تاريخ المستودع؟

- البحث عن مساري ترحيل الأرشيف ومسار `20260920155456_harden_credit_status_authorization.sql` في تاريخ GitHub المتاح لم يُظهر سجل commit يمكن اعتماده لاستعادة الأصل.
- البحث النصي المتاح عثر على ترحيلات لاحقة تعدّل سياسات `credit_accounts` و`credit_periods`، لكنه لم يثبت أصل DDL المطابق للإنتاج.
- لذلك لا نملك حتى الآن سلسلة أدلة كافية لإعادة بناء baseline تاريخي بأمان.

## 4. خطة الحل الآمنة

1. استخرج قائمة الترحيلات المطبقة كاملة من الإنتاج، مع الأسماء والتوقيتات والـchecksums إن كانت متاحة، بقراءة فقط.
2. استرجع الـDDL الأصلي من مصدر موثوق مستقل: commit تاريخي يمكن التحقق منه، artifact إصدار موقع/موثّق، أو سجل نشر موثوق يربط الـDDL بالنسخة الحية.
3. قارن الأعمدة والأنواع والـdefaults والقيود والفهارس والمشغلات والدوال وRLS والسياسات والصلاحيات.
4. أنشئ قاعدة PostgreSQL/Supabase تجريبية معزولة، وأعد تشغيل السلسلة الكاملة من الصفر.
5. لا تُعد كتابة ترحيل مطبقًا ولا تغيّر طابعه الزمني. أضف تصحيحًا جديدًا فقط بعد فهم المصدر والاعتماديات ومراجعة الخطة.
6. إذا تعذّر استرداد التاريخ الأصلي، فاطلب موافقة صريحة منفصلة على **fixture اختبار فقط** مشتق من مخطط الإنتاج الحالي، مع توثيق واضح أنه ليس baseline تاريخيًا. لا تُسجّل fixture باعتباره تاريخًا حقيقيًا، ولا تطبقه على الإنتاج.
7. لا ترفع بوابة إعادة تشغيل الترحيلات إلى PASS حتى تنجح السلسلة الكاملة في قاعدة نظيفة ويُراجع فرق المخطط.

## 5. ما لا يُسمح به

- لا اختلاق baseline أو بيانات تاريخية.
- لا اعتبار الأرشيف وحده مرجعًا موثوقًا للإنتاج.
- لا تطبيق ترحيلات الائتمان أو RC456/RC463/RC464 مباشرة على الإنتاج لمعالجة فشل replay.
- لا تغييرات إنتاجية أو grants أو نشر وظائف دون موافقة صريحة وخطة مراجعة.

## القرار الحالي

**BLOCKED / NOT CERTIFIED.** المانع محدد، والفروق معروفة جزئيًا، لكن provenance الأصلي غير مثبت. الخطوة الآمنة هي استعادة مصدر تاريخي موثوق أو الحصول على موافقة منفصلة على fixture اختبار معلّم بوضوح، ثم إعادة تشغيل السلسلة كاملة في بيئة معزولة.
