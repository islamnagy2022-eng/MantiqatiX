# حارس تعارض إصدارات ترحيلات Supabase

## الغرض
تمنع هذه الضوابط تعارض أرقام الترحيلات ذات 14 رقمًا على مستويين:

1. فحص محلي داخل كل فرع للتأكد من عدم إضافة إصدار مكرر جديد.
2. فحص عبر طلبات الدمج المفتوحة التي تستهدف الفرع الأساسي نفسه، لاكتشاف التعارضات التي لا تظهر داخل أي فرع منفرد.

## طريقة التحقق
- يعمل `scripts/validate-migration-version-uniqueness.mjs` على أسماء الملفات داخل المستودع.
- يعمل `scripts/validate-open-pr-migration-collisions.mjs` على الملفات التي غيّرها طلب الدمج الحالي، ثم يقارنها بملفات الترحيلات المتغيرة في طلبات الدمج المفتوحة الأخرى ذات الفرع الأساسي نفسه.
- يحتوي فاحص التعارضات عبر طلبات الدمج على اختبار ذاتي باستخدام بيانات اصطناعية؛ لا يحتاج الاختبار الذاتي إلى اتصال خارجي.
- يعتمد الفحص عبر GitHub API على `GITHUB_TOKEN` بصلاحية قراءة طلبات الدمج فقط.

## حدود الضمان
هذه الضوابط لا تثبت أن ترحيلًا لم يُطبّق في الإنتاج، ولا تقارن محتوى قاعدة البيانات تلقائيًا بمحتوى ملف SQL. يجب مراجعة `supabase_migrations.schema_migrations` والحالة الفعلية للكائنات قبل الإطلاق.

## تعارض معروف يتطلب تسوية
خلال مراجعة 2026-10-10 ظهر الإصدار `20261009170000` في مسارين مفتوحين:
- RC430 الخاص بمعالجة نجاح Webhook للاشتراك ضمن PR #84.
- ترحيل صلاحيات MantiGO ضمن PR #95.

لا تحل هذه الضوابط التعارض تلقائيًا، ولا يجوز معالجة التعارض بإعادة تسمية ترحيل مطبق على الإنتاج. يجب اختيار مسار قانوني واحد بعد مراجعة الاعتماديات والاختبارات وسجل الإنتاج.
