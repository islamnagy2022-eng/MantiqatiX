# MantiqatiX — قائمة إكمال النسخة التجريبية والموديولات
تاريخ إعداد القائمة: 2026-10-21
المستودع: islamnagy2022-eng/MantiqatiX
الحالة العامة: **قائمة تنفيذ — لا تعني أن البنود مكتملة أو مختبرة**.

## قواعد العمل الملزمة
- [ ] تنفيذ موديول واحد في كل مرة، بدءًا بالمطاعم، ثم اختباره قبل الانتقال للموديول التالي.
- [ ] لكل بند: فحص المصدر الحالي → تحديد العقد والاعتماديات → تنفيذ صغير قابل للمراجعة → اختبارات آلية → اختبار واجهة → اختبار صلاحيات وعزل → توثيق النتيجة.
- [ ] التمييز دائمًا بين IMPLEMENTED وTESTED وDEPLOYED وVERIFIED؛ وجود الكود لا يعني أنه يعمل على الموقع المنشور.
- [ ] لا إنشاء بيانات وهمية في قاعدة الإنتاج، ولا مدفوعات أو معاملات مالية تجريبية حقيقية.
- [ ] لا تعديل صلاحيات أو سياسات RLS أو migrations أو إعدادات Supabase الإنتاجية لمجرد جعل الاختبارات تمر؛ يجب إثبات الحاجة ومراجعة الأثر.
- [ ] لا اعتبار الواجهة التجريبية نظام تشغيل حقيقيًا إذا كانت تستخدم بيانات محلية أو محاكاة.
- [ ] لا أسرار في الواجهة أو المستودع؛ مفتاح Supabase العام فقط في الواجهة، ومفتاح الخدمة يبقى في الخادم.
- [ ] أي وظيفة غير متاحة يجب أن تعرض حالة واضحة للمستخدم، لا نجاحًا وهميًا ولا قائمة فارغة توحي بأن كل شيء سليم.
- [ ] كل شاشة عربية RTL، متجاوبة، قابلة للوصول بلوحة المفاتيح وقارئ الشاشة، وتعرض حالات التحميل والفراغ والخطأ وعدم الصلاحية.
- [ ] لا إعلان اكتمال موديول حتى تنجح اختبارات الوظائف والصلاحيات والربط والتراجع والتوثيق.

## A. بوابة النسخة التجريبية العامة
### الوصول والتنقل
- [ ] التحقق من عنوان الموقع المنشور فعليًا ومسارات GitHub Pages، وتسجيل HTTP status لكل مسار.
- [ ] التحقق من مسار الصفحة الرئيسية والروابط إلى المعاينة ولوحة العمل ولوحة الإدارة وتسجيل الدخول.
- [ ] التحقق من عدم وجود 404 أو روابط نسبية مكسورة أو ملفات JavaScript/CSS/صور لا تُحمّل.
- [ ] التحقق من refresh على المسارات الفرعية، والعودة/التقدم، وفتح الروابط في تبويبات جديدة.
- [ ] توحيد أسماء المنتج والعلامة التجارية والنصوص العربية ورسائل الأخطاء.
- [ ] التأكد من أن كل زر ظاهر ينفذ إجراء حقيقيًا أو يحمل وصف «تجريبي/غير متصل» بوضوح.
- [ ] إزالة البيانات والأرقام والتقييمات الوهمية من أي واجهة قد يظنها الزائر بيانات حقيقية.
- [ ] إضافة حالات loading / empty / error / offline / permission-denied / retry.
- [ ] اختبار عرض الهاتف الصغير والتابلت وسطح المكتب والتكبير 200%.
- [ ] تدقيق تباين الألوان، التركيز المرئي، ترتيب Tab، أسماء الأزرار، العناوين، ورسائل aria-live.
- [ ] فحص console والأخطاء الشبكية وطلبات الشبكة غير الضرورية.
- [ ] التحقق من سياسة الخصوصية وشروط الاستخدام والموافقة على معالجة البيانات وروابط التواصل.
- [ ] فصل معاينة العرض عن بيانات الإنتاج، وعدم إدخال بيانات المستخدم في التخزين المحلي بلا حاجة.
- [ ] توثيق طريقة تشغيل المعاينة وحدودها وما لا تدعمه.

### الدخول والحساب
- [ ] اختبار تسجيل الدخول وتسجيل الخروج وتجديد الجلسة وانتهاء صلاحيتها.
- [ ] اختبار OTP والبريد غير المؤكد وإعادة الإرسال والروابط المنتهية أو المستخدمة سابقًا.
- [ ] اختبار استعادة الحساب ورسائل الخطأ وعدم كشف وجود البريد من عدمه.
- [ ] منع الوصول إلى أي شاشة تشغيلية دون جلسة صالحة وعضوية نشطة.
- [ ] اختبار تغيير العضوية أو الدور أثناء الجلسة وإبطال أي صلاحيات مخزنة قديمة.
- [ ] اختبار مستخدم عادي وموظف ومدير نشاط ومالك نشاط ومدير منصة ضمن بيئة اختبار معتمدة.
- [ ] اختبار فصل المؤسسة والنشاط والفرع والمستخدم والموفر؛ منع IDOR والوصول المتبادل.
- [ ] استخدام مصدر صلاحيات مركزي؛ عدم الاعتماد على إخفاء الأزرار أو قائمة أدوار ثابتة في الواجهة.
- [ ] مراجعة حدود الجلسة ومعدل المحاولات وحماية كلمات المرور المسربة وإعدادات إعادة التوجيه.

### المعمارية والبيانات المشتركة
- [ ] توثيق العقد المركزي للأنشطة والفروع والكتالوج والأسعار والطلبات وحالات الطلب والدفع.
- [ ] تحديد مصدر الحقيقة لكل كيان وعدم إنشاء نسخة ثانية من الأسعار أو الطلبات أو الحسابات.
- [ ] توحيد معالجة الأخطاء وCorrelation ID والرسائل الآمنة للمستخدم.
- [ ] مراجعة سياسات RLS على كل جدول وRPC وEdge Function وفق مبدأ أقل صلاحية.
- [ ] مراجعة جميع عمليات الكتابة المباشرة من الواجهة ونقل العمليات الحساسة إلى مسار خادمي موثوق.
- [ ] التحقق من idempotency والطلبات المتزامنة والتكرار وإعادة المحاولة.
- [ ] مراجعة حدود حجم الطلبات والتحقق من المدخلات وترميز المخرجات ومنع XSS.
- [ ] مراجعة pagination والبحث والفرز والفلاتر والفهارس بناءً على خطط الاستعلام الفعلية.
- [ ] اختبار انقطاع الشبكة وإعادة الاتصال والتعارض بين التحديثات.
- [ ] التحقق من النسخ الاحتياطي والاستعادة والتراجع ومراقبة الأخطاء والتنبيه.

## B. الموديول الأول — المطاعم والمطابخ (أولوية التنفيذ)
**الموجود بحسب مراجعة المصدر:** يوجد `web/restaurant-module.js` يقرأ القائمة والطلبات والطاولات والمخزون من Supabase؛ إنشاء الطلب يستعمل كتالوجًا مركزيًا ودالة `order-create`؛ تحديث حالة الطلب يستعمل `order-status-update`. يوجد توثيق سابق لمسار الطلب الموحد وحدود الأمان. هذه دلائل على وجود تنفيذ جزئي، وليست شهادة اكتمال. يجب إعادة اختبار كل نقطة على رأس الفرع الحالي.
### B1. فتح الموديول والعضوية والنطاق
- [ ] التأكد من أن الموديول يُحمّل مرة واحدة فقط ولا ينشئ MutationObserver أو interval مكررًا عند التنقل.
- [ ] استبدال فحص الأدوار الثابت في الواجهة بعقد RBAC مركزي متاح للمشروع، بعد التحقق من أسماء الموارد والأفعال المدعومة.
- [ ] تحديد العضوية النشطة والنشاط والفرع من مصدر موثوق، والتحقق من أن اختيار العضوية لا يوسّع النطاق.
- [ ] معالجة غياب العضوية أو تعدد العضويات أو عضوية معلّقة/موقوفة/منتهية.
- [ ] منع استخدام نطاق فارغ أو غير مكتمل في أي قراءة أو كتابة.
- [ ] عدم الاعتماد على owner_user_id وحده لتفويض المدير والموظف؛ يجب أن يكون القرار خادميًا وسياسات RLS.
- [ ] التحقق من أن فشل أي استعلام لا يُعرض على أنه «لا توجد بيانات».
- [ ] اختبار الدخول المباشر إلى شاشة المطاعم دون المرور بالتنقل الطبيعي.

### B2. لوحة المطعم
- [ ] إظهار اسم النشاط والفرع والوقت وآخر تحديث.
- [ ] مؤشرات الطلبات حسب الحالة، والمبيعات المعتمدة، ومتوسط الطلب، والأصناف منخفضة المخزون.
- [ ] تحديد مصدر كل مؤشر وتعريفه؛ عدم احتساب الإيراد من إجمالي طلبات ملغاة أو غير مدفوعة.
- [ ] نطاق زمني وفلاتر الفروع وصلاحيات كل مؤشر.
- [ ] حالات loading/empty/error/retry لكل بطاقة.
- [ ] زر تحديث لا يسبب طلبات متزامنة أو مضاعفة.
- [ ] اختبار الأرقام مع استعلامات مرجعية مستقلة.

### B3. قائمة الطعام والكتالوج
- [ ] عرض الأصناف مع بحث وفلاتر وتصنيفات وترقيم صفحات.
- [ ] إضافة/تعديل/إخفاء صنف وفق صلاحية محددة.
- [ ] التحقق من الاسم والوصف والفئة والسعر والعملة وحدود الطول والقيم العددية.
- [ ] منع السعر السالب وNaN والقيم الضخمة والدقة العشرية غير المدعومة.
- [ ] دعم صور الأصناف ورفعها إلى Storage مع التحقق من النوع والحجم والمسار والصلاحيات.
- [ ] دعم التوافر المؤقت ونفاد الصنف وإعادة تفعيله.
- [ ] دعم الإضافات والخيارات والأحجام والمجموعات والحد الأدنى/الأقصى للاختيار.
- [ ] دعم السعر الأصلي والعرض فقط من مصدر مركزي موثوق.
- [ ] ربط الأصناف بالكتالوج المركزي والأسعار النشطة وعدم اعتبار سعر المتصفح نهائيًا.
- [ ] منع تكرار الصنف بالضغط المتكرر، ومعالجة تضارب تعديل صنف من مستخدمين.
- [ ] تأكيد قبل الحذف/الإخفاء مع الحفاظ على الطلبات التاريخية.
- [ ] سجل تدقيق لتغييرات السعر والتوافر والوصف ومن قام بالتغيير.
- [ ] اختبار مستخدم قراءة فقط ومدير فرع ومدير نشاط وموظف.

### B4. الطلبات ودورة الحياة
- [ ] عرض الطلبات من جدول `orders` المركزي فقط، لا من جدول قديم متوازٍ.
- [ ] بحث برقم الطلب والعميل، وفلاتر الحالة والتاريخ والفرع وقنوات الطلب.
- [ ] صفحة تفاصيل كاملة: العناصر والخيارات والكميات والأسعار والخصومات والضريبة والتوصيل والإجمالي والملاحظات.
- [ ] التحقق من أن إجمالي الطلب محسوب خادميًا ولا يثق في قيم العميل.
- [ ] حالات الطلب المعتمدة وانتقالات مسموحة فقط وفق state machine خادمي.
- [ ] إظهار سبب رفض الانتقال ورسالة آمنة للمستخدم.
- [ ] إلغاء الطلب وفق السياسة وعدم إلغاء طلب مدفوع دون مسار استرداد معتمد.
- [ ] منع الانتقال إلى حالة نهائية ثم الرجوع عنها دون إجراء خادمي مسموح.
- [ ] اختبار الضغط المكرر وطلبات الشبكة المتزامنة وidempotency.
- [ ] التحقق من أن كل طلب يظهر للنشاط والفرع الصحيح فقط.
- [ ] إشعارات تغيير الحالة وربط النقر بالتفاصيل.
- [ ] طباعة/تنزيل ملخص الطلب دون تسريب بيانات غير لازمة.
- [ ] اختبار العميل والمطعم والموظف والتوصيل عبر حسابات اختبار معتمدة.

### B5. المطبخ وتجهيز الطلبات (KDS)
- [ ] شاشة مطبخ مخصصة للطلبات الجديدة وقيد التحضير والجاهزة.
- [ ] ترتيب زمني وأولوية ووقت انتظار ومؤشر تأخير.
- [ ] تحديث آمن للحالات من المسار المركزي.
- [ ] تحديث تلقائي أو realtime بعد إثبات صلاحية قناة الاشتراك؛ لا استبدال polling دون قياس.
- [ ] تنبيه صوتي/مرئي قابل للتعطيل وعدم تكرار التنبيه بلا نهاية.
- [ ] تقسيم محطات التحضير إن كانت مدعومة (مشويات/مشروبات/حلويات).
- [ ] وضع شاشة كاملة وإيقاف الشاشة دون فقد الحالة.
- [ ] اختبار فقد الشبكة واستعادة التحديثات ومنع تنفيذ انتقال مرتين.

### B6. الطاولات والحجوزات
- [ ] عرض الطاولات حسب الفرع والسعة والحالة.
- [ ] إضافة/تعديل/تعطيل طاولة مع التحقق من رقم الطاولة والسعة.
- [ ] تصحيح واختبار تعيين الحالة الحالية عند تعديل الطاولة.
- [ ] منع تكرار رقم الطاولة داخل الفرع من خلال قيد خادمي.
- [ ] حالات فارغة/مشغولة/محجوزة/تنظيف/خارج الخدمة.
- [ ] إنشاء وإلغاء وتعديل حجز مع وقت البداية والنهاية وعدد الضيوف وبيانات اتصال مناسبة.
- [ ] منع الحجز المتداخل على الطاولة نفسها.
- [ ] ربط الطاولة بالطلب والفاتورة عبر مسار معتمد، وعدم تغيير مبلغ الفاتورة مباشرة من المتصفح.
- [ ] إغلاق الجلسة وإخلاء الطاولة فقط بعد تحقق حالة الطلب/الفاتورة.
- [ ] اختبار تعارض حجزين متزامنين وصلاحيات الموظف.

### B7. المخزون والمشتريات
- [ ] عرض الرصيد والوحدة وحد التنبيه والتكلفة والمورد.
- [ ] تعريف الوحدات والتحويل بينها بدقة (قطعة/كجم/جرام/لتر).
- [ ] عدم تعديل الرصيد مباشرة كقيمة عادية؛ كل حركة يجب أن تكون حركة مخزون موثقة.
- [ ] إضافة استلام/صرف/هالك/تسوية/تحويل بين الفروع عبر مسار خادمي.
- [ ] منع الرصيد السالب أو السماح به فقط وفق سياسة صريحة.
- [ ] حساب تكلفة المخزون بطريقة معتمدة وتوثيق التغييرات.
- [ ] ربط وصفات الأصناف (BOM/Recipes) بخصم مكونات عند مرحلة الطلب المحددة.
- [ ] تنبيهات حد الطلب وإعادة التوريد.
- [ ] الموردون وأوامر الشراء والاستلام والفواتير حسب نطاق ERP المعتمد.
- [ ] سجل حركة قابل للمراجعة: الفاعل والسبب والكمية قبل/بعد والمرجع الزمني.
- [ ] اختبار التزامن ومنع خصم المخزون مرتين عند تكرار الحدث.
- [ ] مطابقة المخزون النظري مع الجرد الفعلي.

### B8. الدفع والفواتير والمالية
- [ ] عرض حالة الدفع من المصدر المالي المركزي فقط.
- [ ] فصل قيمة الطلب عن المدفوع والمسترد والعمولة والتسوية.
- [ ] عدم إضافة مدفوعات أو محافظ أو قيود مالية مباشرة من واجهة المطعم.
- [ ] ربط بوابة الدفع عبر عقد الدفع المعتمد فقط.
- [ ] اختبار webhook signature/HMAC وreplay/idempotency والربط بالطلب الصحيح في بيئة sandbox معتمدة.
- [ ] فواتير وإيصالات بأرقام مرجعية من الخادم.
- [ ] قواعد الضريبة والخصم والتوصيل من إعدادات خادمية موثقة.
- [ ] منع الإلغاء أو رد الأموال غير المتسق مع حالة الدفع.
- [ ] تقارير تسوية ومطابقة مع المصدر المالي.
- [ ] لا تفعيل real-money E2E إلا بموافقة صريحة وبيانات اختبار/حساب معتمد.

### B9. التوصيل والاستلام
- [ ] تحديد نمط تنفيذ الطلب: داخل المطعم/استلام/توصيل.
- [ ] العنوان وملاحظات التوصيل وفق أقل قدر من البيانات.
- [ ] تعيين مندوب وحالة التوصيل إذا كان المسار مدعومًا.
- [ ] إثبات التسليم وسياسة فشل التسليم والإرجاع.
- [ ] تقدير زمن التوصيل من قواعد موثوقة، لا أرقام ثابتة مضللة.
- [ ] حماية بيانات العميل وأرقام الهواتف وعناوينه حسب الدور.
- [ ] إشعارات الطلب والتوصيل مع منع التسريب بين العملاء.

### B10. التقارير وإدارة الفروع
- [ ] تقرير مبيعات حسب الفترة والفرع والصنف والحالة.
- [ ] تقرير الأصناف الأكثر طلبًا والملغاة والمرتجعة.
- [ ] تقرير المخزون والهالك والتكلفة والهامش فقط إذا توفرت مصادر محاسبية موثوقة.
- [ ] تصدير CSV آمن من البيانات المصرح بها مع معالجة CSV injection.
- [ ] مقارنة الفروع مع منع خلط tenant/business.
- [ ] تدقيق صلاحيات التقارير والحقول الحساسة.
- [ ] عدم تقديم التقارير كحقيقة مالية معتمدة قبل مطابقة القيود والتسويات.

### B11. الجودة والأمان وإتاحة الاستخدام
- [ ] إصلاح وإعادة اختبار جميع أخطاء JavaScript وطلبات الشبكة.
- [ ] اختبارات وحدات للتحقق من المدخلات والحالات وانتقالات الطلب.
- [ ] اختبارات عقد للكتالوج المركزي وEdge Functions.
- [ ] اختبارات RLS سلبية وإيجابية لمستخدمين ونشاطين وفرعين.
- [ ] اختبارات XSS وحقن مدخلات وIDOR وتجاوز الأدوار.
- [ ] اختبار فشل استعلام واحد من أصل عدة استعلامات وعدم إخفاء الفشل.
- [ ] اختبار منع التكرار عند النقر السريع وفقد الاستجابة ثم إعادة المحاولة.
- [ ] اختبار شاشة صغيرة ولوحة مفاتيح وقارئ شاشة وتباين الألوان.
- [ ] اختبار المتصفحات المستهدفة وإصدارات الهاتف.
